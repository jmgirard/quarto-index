### D-001 (2026-08-16): entry= values are structured format-neutral data, not raw LaTeX

**Context:** M01's plan made `entry="..."` a raw LaTeX pass-through (sub-entries written in imakeidx syntax). The design interview adopted IP1: mark values must be meaningful to every future back-end.
**Decision:** Entry values are structured data the extension parses and realizes per format (e.g., sub-entry separation interpreted by the extension itself, remainder escaped); raw back-end code is never accepted in mark values.
**Consequences:** M01's escaping-design scope needs a gated plan amendment before implementation. Future back-ends consume the same entry semantics. Admitting raw LaTeX later would require an explicit recorded reversal of IP1.

### D-002 (2026-08-18): An empty index level is not a level

**Context:** M11 found that a leading empty level in `entry=` (`entry="!Cats"`) made the LaTeX back-end emit a null field, which makeindex rejects — dropping the whole entry while exiting 0 with no warning. Three semantics had to be settled, and D-001 records this same class of choice about what `entry=` values mean.
**Decision:** An empty level prints nothing and is therefore not a level: it is dropped once, format-neutrally, before any back-end sees it. A value that is only empty levels falls back to the mark's visible text, or indexes nothing where there is none. A sort level is dropped together with the entry level it was written for, never re-aligned onto a level it was not written for; the loss is reported.
**Consequences:** `entry="!Cats"` and `entry="Cats!"` both index as `Cats`, in every back-end, and no entry can file under an empty string. Depth is counted after the drop, so a stray `!` cannot push an entry over the LaTeX three-level ceiling. The rule is format-neutral by its own justification — a level that prints nothing is not a level — and so lives in the shared parse layer, unlike the three-level ceiling, which stays in the back-end that imposes it. From the first tagged release this is IP3-bound syntax.

### D-003 (2026-08-19): Output the index tool cannot consume is the extension's, not the toolchain's

**Context:** M15 fixes a term marked both plainly and with a cross-reference, which makes the LaTeX back-end emit two rival encapsulations for one index key; makeindex rejects the pair and Quarto turns that into a failed render. GP2 says the contract ends at correct emitted output and that a toolchain's failure modes are documented, never detected or managed, which reads against fixing it at all.
**Decision:** A pair of commands the documented index tool provably cannot process is incorrect emitted output, not a toolchain failure, so repairing it sits inside GP2 rather than trading against it. The reading is deliberately narrow: it licenses changing what the extension emits when the extension's own output is unusable, never detecting or working around a failure the emission did not cause — a missing font, a distribution quirk, a user's own preamble.
**Consequences:** M15 proceeds without amending GP2. A later proposal to detect or manage a toolchain failure the extension did not cause is still governed by GP2 as written and needs its own justification. GP2's "known failure modes documented" continues to govern what the README says about failures this extension cannot prevent.


### D-004 (2026-08-20): Byte-level output-neutrality evidence is rejected as the refactor oracle

**Context:** `tests/byte-diff.sh` rendered every merge-base fixture twice and diffed the `.tex` byte for byte. Planning M17 (splitting the 2,729-line filter) asked whether to widen it to HTML and to the three book projects, which the 29-of-38 non-recursive fixture list, the non-hermetic base checkout, and the one-file clean-tree guard all left uncovered.
**Decision:** Widening was refused as the checker-regress shape, and the script is deleted rather than simplified: its own header disclaims it as a check, it duplicates coverage the ~100-check acceptance suite has, and a byte-diff fails on invisible whitespace changes — the shape tracking-rules names as a defect in the test ("a test that breaks under a behavior-preserving refactor"). The acceptance suite is the sole oracle for output neutrality.
**Consequences:** M17 verifies the split through the suite's pass/fail set plus an install-parity probe, with no merge-base output comparison; a rendered-output change no check probes would pass. That residual risk is recorded on the acceptance-suite hardening candidate row. Restoring byte-level evidence takes a superseding entry.

### D-005 (2026-08-20): Where a back-end folds levels, it judges cross-reference targets against what it prints

**Context:** M14 made the "target names nothing this document indexes" report format-neutral, resolving targets against the level paths the author wrote, on the grounds that whether a target names an indexed term is a fact about the document rather than about a back-end (IP1). M18 finds the LaTeX three-level fold breaks that in both directions: a target naming the folded path draws that report *and* the fold's own self-reference report, which contradict each other, and a target naming a written path the fold rewrites resolves silently while the printed index contains no such path. D-003 is the governing frame — a cross-reference the documented index tool prints and no reader can follow is incorrect emitted output, not a toolchain failure.
**Decision:** A back-end that folds levels folds cross-reference targets by the same rule and resolves them against the paths its entries print. The format-neutral report stands unchanged for every format that imposes no ceiling, and the format-neutral self-target comparison is untouched — M10's gate choice against moving that comparison into the back-ends still holds. Only the resolution set becomes back-end-relative, and only where a ceiling exists.
**Consequences:** In LaTeX the report no longer fires for the fold-induced shapes in `examples/self-xref.qmd`, superseding the last sentence of M14's AC4 for that back-end alone; HTML and back-end-less formats keep the counts M14 pinned, and the counts themselves live in M18's criteria. A future back-end with a ceiling inherits the rule; one without inherits nothing. D-002's placement rule is unchanged: the ceiling stays in the back-end that imposes it, and the empty-level drop stays shared. Restoring a single format-neutral resolution set takes a superseding entry.

### D-006 (2026-08-21): A reported level count names the levels it is over

**Context:** A value in `entry=`, `sort=` or a cross-reference target has three level counts — what the author wrote, what survives the empty-level drop (D-002), and what the LaTeX three-level fold prints. Three warnings name one of these and say which either not at all or misleadingly: the folded-target report names the post-drop count of a target the author wrote deeper (M18 review F9), and the extra-sort report attaches "before empty levels are dropped" to two counts no drop touches (M13 review F4). M13 shipped this subject once already and left both open.
**Decision:** A warning reporting a count of index levels names which levels the count is over, and gives the count the author wrote alongside it wherever the two differ. This governs what a number is called, never what it is: D-002's rule that depth is counted after the drop is unchanged, and so is every number these reports compute.
**Consequences:** The written count is carried to the two fold reports, which do not hold it today, so what `target_levels` and `drop_empty_levels` already compute travels to the LaTeX back-end. On a mark that both loses an empty level and crosses the ceiling, the empty-level report and the entry-fold report name the same pair of counts on consecutive lines; suppressing one would need the two reports to know about each other, and was refused. The rule binds the three reports M19 names and any later report that comes to name a level count. It was deliberately not mechanized as a sweep, because the message-distinctness scan cuts each message expression at `:format(` and so never reads its numbers — a gap recorded on the acceptance-suite hardening candidate row. A report whose count has no drop to distinguish is outside the rule.

### D-007 (2026-08-21): Per-locator styling leaves makeindex's encapsulation channel

**Context:** M20 gives one occurrence of a term an emphasized locator. Realized as a makeindex encapsulation, that breaks the render: makeindex's conflict predicate is same key, same page, any byte difference in the encapsulation string — bare-versus-encapsulated included — and a Pandoc filter cannot know page numbers. Distinguishing the principal mark through the key, the printed field or the sort field files it as a different entry instead, which corrupts the index rather than styling it. makeindex itself warns at exit 0 and writes a correct `.ind`; Quarto alone fails the render, on a regex over the `.ilg` transcript. RB01/RR01 (`cairn/reviews/archive/`) verified each leg.
**Decision:** Per-locator styling is not expressible through what `\index` commands say, and this back-end realizes it on a second, typeset-time channel instead: every locator mark of a key carrying a role emits one uniform per-key encapsulation, so a conflict is unreachable by construction rather than merely unexercised, and the role is registered from the mark's own position into the `.aux` and applied when the index is typeset. Warning-suppression and engine-swap recoveries are refused — each is blanket, masks the collision class D-003 covers, and is user metadata a filter cannot set anyway.
**Consequences:** M20 builds the subsystem; M21's page ranges inherit both the channel and its one known gap, a registered page folded inside a range printing unemphasized. The impossibility is permanent, so a later proposal to style a locator through the encapsulation channel is answered here rather than re-derived. Refusing the subsystem on cost leaves exactly one fallback — the LaTeX back-end reports the role as unrealized (IP1) — and taking it needs a superseding entry.

### D-008 (2026-08-22): An author-written range registers its own printed page string (annotates D-007)

**Context:** D-007 puts per-locator styling on a typeset-time channel: the principal mark writes its ordinal and `\thepage` to the `.aux`, and `\printindex` looks each printed page up in that registry. A page range prints as one string — `3--7` — which matches no per-page registration, so D-007 recorded a principal page inside a range printing unemphasized as the channel's one known gap and left it to M21.
**Decision:** That gap divides in two, and M21 closes only the half the filter can see. A range the AUTHOR wrote is known to the filter, so its opening and closing marks each register their own page, and the pair is composed into the printed range string and registered against the key's ordinal exactly as a single page is; the opening page is registered alone as well, since makeindex prints a same-page pair as one page rather than as a range. A range makeindex FOLDS out of consecutive pages is not known to the filter at all — no mark says a range exists there — and stays unemphasized.
**Consequences:** D-007's channel is extended, not superseded: the uniform per-key encapsulation, the ordinal and the registry are unchanged, and one further `.aux`-borne command joins the four. The prose recording the gap — README's principal-locator section and `core.lua`'s subsystem comment — narrows to the folded case, which is a correction of current knowledge rather than an addition. The ROADMAP candidate row asking whether a folded range is emphasized whole stands, now naming the only remaining half.

### D-009 (2026-08-22): A range pairs within one Pandoc process, never across a book's chapters

**Context:** M21's ranges pair two marks of one entry. In every format but an HTML book that pairing happens inside one Pandoc process — a single document is one process, and a PDF book is one merged document. An HTML book is not: each chapter renders in its own process, so the pairing has to be re-derived by whichever chapter reads the sidecar store. Three review rounds each found exactly one defect in that re-derivation, and each was the same mistake — a value resolved in one chapter's process read as raw in another's — in the record's `range` field, then the book's verdict, then the record's `role`. The store's per-mark record mixes what the author wrote with what that chapter concluded, and its current shape cannot express the boundary.
**Decision:** A range pairs within one Pandoc process and nowhere else. In an HTML book a `range=` mark indexes as though the attribute were absent, and the book says so once rather than pairing across chapters. This is not a judgement that cross-chapter ranges are undesirable; it is that pairing them needs a per-chapter record which separates the author's own values from a chapter's resolutions, and that design is not M21's to settle.
**Consequences:** D-008's Consequences say "one further `.aux`-borne command joins the four"; it is two — `quartoindexrangeat` and `quartoindexrangeto` are the names an `.aux` line carries, and the other two are emitted at the marks — and this entry supersedes that count, which matters because the stale-`.aux` exposure is counted in those names. M21 ships ranges for single documents in both back-ends and for PDF books, and the cross-chapter case leaves its scope. The candidate row promotes on that record shape rather than on the feature being wanted — the conflation is what produced one defect per review round, so a proposal that keeps the present record shape is answered here rather than re-derived, and takes a superseding entry. D-008's range registration is untouched: it is LaTeX-side and a PDF book is one document.

### D-010 (2026-08-22): A chapter's own range pairs in an HTML book (annotates D-009)

**Context:** D-009's Decision paragraph says "In an HTML book a `range=` mark indexes as though the attribute were absent." Written at the cross-chapter descope, the sentence overgeneralizes: a chapter is one Pandoc process, so a range whose two marks are in one chapter pairs there — shipped behavior M21's fixtures and README document.
**Decision:** That sentence narrows to a range whose marks are in different chapters. D-009's title — a range pairs within one Pandoc process, never across a book's chapters — already states the rule; everything else in D-009 stands.
**Consequences:** Reading only; no code or scope change.


### D-011 (2026-08-23): A source-shape scan is retired or narrowed, never widened

**Context:** The acceptance-suite-hardening candidate row carries five ways the `tests/scans/` checks miss what they read: four scans take the FIRST regex match over a source set that became multi-file at M17, so a stale duplicate definition masks the live one; the twelve-scan count pin counts files under `tests/scans/` rather than the source-reading sites it claims to hold, so a one-for-one swap passes it; `warn-distinct.py` cuts each message expression at `:format(` and so reads neither the numbers nor the text built there; the moved-definition probe writes every relocated definition into one `modules/moved.lua`, exercising one member of a nine-member family; and no check guards M17-AC1's one-definition-per-entry-point rule at all. Planning M25 asked whether to widen each of them.
**Decision:** Widening is refused, on D-004's precedent and for the same reason it gave. A scan that pins names and shapes in source certifies a property it never asserts — the M23 lesson, drawn from six such gaps found across two review rounds, every one of them by someone building the broken tree by hand while the scan exited 0. Each scan is therefore retired, or narrowed to what it reads with its header comment saying so. Where a property is positional, the evidence is a render: a render cannot pass a tree whose render fails.
**Consequences:** M25 removes the twelve-scan pin, disposes the four FIRST-match scans one at a time, narrows `warn-distinct`'s promise rather than teaching it to read `:format(` arguments, and leaves M17-AC1 unguarded by any scan. The coverage that leaves is coverage the scans only appeared to give; the residual risk — a source-shape regression no render probes — is recorded on the acceptance-suite-hardening candidate row beside D-004's own. This entry governs scans over the extension's SOURCE. It does not touch checks over rendered output, and M24's repair of where a check reads from is outside it entirely: that leaves every promise unchanged. Restoring a widened source scan takes a superseding entry.

### D-012 (2026-08-23): A same-tree state-pollution comparison is not the refactor oracle D-004 refused (annotates D-004)

**Context:** D-004 deleted `tests/byte-diff.sh` and closed with "Restoring byte-level evidence takes a superseding entry", leaving the acceptance suite as the sole oracle for output neutrality. M26 needs to prove that a document's index output does not depend on what ran before it in the same Lua state, and the only evidence that covers every one of the 17 accumulators — including `principal_emitted`, which reaches the preamble, and `principal_ordinals`, whose value reaches the `.aux` registry — is a byte comparison of two renders.
**Decision:** D-004's bar does not reach this comparison, and no superseding entry is needed. What D-004 refused was a MERGE-BASE oracle: two trees, differing by a refactor, compared byte for byte — the shape tracking-rules names as a defect in the test, because a behavior-preserving change breaks it on invisible whitespace. M26's comparison runs both sides off ONE tree, differing only in whether a test-only filter drove a synthetic document through the pass list first. A refactor moves both sides identically, so the failure mode D-004 named is unreachable here by construction, and the comparison's subject is the milestone's own deliverable rather than a proxy for it.
**Consequences:** M26's AC1 and AC2 rest on `cmp -s` over a captured `.tex` and a captured HTML page. D-004 is otherwise untouched: the acceptance suite remains the sole oracle for output neutrality across commits, `tests/byte-diff.sh` stays deleted, and its residual risk stays on the acceptance-suite-hardening candidate row. This entry licenses same-tree comparisons whose two sides differ only in a deliberately injected condition; a byte comparison across two commits still takes the superseding entry D-004 demands.

### D-013 (2026-08-23): A finding about current behavior is a known issue, not a candidate row

**Context:** Every review that found something appended it to the nearest `cairn/ROADMAP.md` candidate row or `cairn/LESSONS.md` line, because neither file's header said where a finding belongs and a candidate row was the only place accumulating them. Rows grew clauses that propose no work — how the extension behaves today, what a check does not cover — and both files reached their weight caps; M27's file records the sizes and the per-row figures.
**Decision:** Three records divide the material. `cairn/DESIGN.md`'s `## Known issues` holds a statement about how the extension or its acceptance suite behaves today, a gap in what a check covers included; each entry carries a stable `KI<n>` label, its own text, and the review it came from. `cairn/ROADMAP.md`'s `## Candidates` holds work this repo might do — one row stating the work and its promotion condition, pointing at the `KI<n>` labels that motivate it and restating none of them. `cairn/LESSONS.md` holds transferable craft, a mistake a future milestone could repeat, and never a fact about this repo's present state; a lesson that has become one takes the ownership exit to `## Known issues`.
**Consequences:** A row that proposes nothing is not a candidate — its content is a known issue and the row does not exist. A review recording a finding writes a `## Known issues` entry, and a candidate row only where it wants work done. `KI<n>` labels are assigned in order and never reused, so a pointer survives an entry being reworded; the milestone that closes an issue strikes its entry and rewrites any row pointing at it in the same commit. The `## Candidates` comment in `cairn/ROADMAP.md` and the header comment in `cairn/LESSONS.md` name this entry. This governs where a record goes, not what is kept: M27 moved every clause and dropped none.

### D-014 (2026-08-23): A reported block or chapter position names the sequence it counts (annotates D-006)

**Context:** D-006 made a warning reporting a count of index LEVELS say which levels the count is over, and left outside its rule any report whose number has no empty-level drop to distinguish. Three reports sit in that gap: the emptied-place and duplicate-marker reports in `marker.lua` name a top-level-block position, and the chapter-count report in `book.lua` names a number of chapters. Nothing said what any of those numbers is counted over, and the `resolve_markers` comment and the `marker-shapes.qmd` manifest comment both called the block position the author's own. It is not: Quarto expands includes and executable cells before any filter runs, and `examples/marker-position.qmd` holds a marker written as its third top-level block and reported at its fifth.
**Decision:** A warning reporting a position or a count over a sequence names that sequence. A block position says it is counted over the document as this filter received it, after Quarto expanded any includes and executable cells, so it can differ from the position in the author's source file; a chapter count says it is over the files the book renders, in the order the book's render list gives them. Where a report names two numbers, each is named where it is printed. The author's own source position is not offered alongside the reported one: the expansion has already happened by the time the filter runs and nothing records where a block came from, so the report qualifies its number rather than printing a second one it cannot compute.
**Consequences:** The block-position clause is one shared string in `marker.lua`, so the two reports there cannot drift apart. The evidence is emitted text in captured render logs and never a scan of the filter's source, which is D-011's rule and the reason no check here reads a `warn` literal. KI21 narrows to the injection kinds no fixture exercises; KI25 closes. Naming the chapter FILE in a book report is M29's subject, not this entry's. A later report that comes to name a position or a count over a sequence inherits the rule; a report whose number indexes into no sequence is outside it, as it is outside D-006.

### D-015 (2026-08-24): `[` and `]` stay out of the LaTeX escape table

**Context:** Pandoc's LaTeX writer escapes `[` and `]` in body text, and the filter's `LATEX_LITERAL` table does not carry them. KI1 recorded that gap from M01 and called it harmless in practice without saying what had been tried, and a ROADMAP candidate row asked for the two characters to be added. The concern behind the row is real in shape: `theindex` builds its entries with `\item`, and a `\item` that takes an optional argument would swallow a leading `[`.
**Decision:** The two characters stay out of the table. Probed at this plan gate under the engine the extension ships against, with `imakeidx` loaded: index entries leading with a bracket, holding one medially, and trailing a closing bracket each compiled through both LaTeX passes, were accepted by makeindex without rejection, and typeset in the index exactly as written. `theindex` redefines `\item` without an optional argument, which is why the leading case survives. Escaping them anyway would change what an entry sorts under and ripple through the probe set and several manifests, for no behavior a reader can see.
**Consequences:** KI1 is struck and its candidate row removed. `PROBE_CHARS` and `LATEX_LITERAL` keep the 16 characters they name, and `tests/scans/latex-escape-table.py` keeps holding the two to each other. This settles the two brackets, not the table: a character shown to print wrongly is an IP2 defect and joins the table on that evidence. The gap the row actually sat on — that the suite proves all 94 printable ASCII characters compile and are accepted, and proves only 16 of them print — is M30's subject, not this entry's. Reopening takes a superseding entry, whose evidence would be a shipping document class or package whose `theindex` `\item` takes an optional argument.

### D-016 (2026-08-24): IP2's non-ASCII promise is conditional on the document's PDF engine and main font (narrows IP2; annotates D-003)

**Context:** IP2 promised that any characters in a visible term appear correctly in the index, non-ASCII included, with no condition attached. Probes at M33's plan and implement gates show that promise is false as written, and not because of anything the filter does: under Quarto's default `pdflatex` a Greek index entry stops the render outright with `not set up for use with LaTeX`, and under `xelatex` with the default main font the render succeeds at exit 0 while every glyph the font does not carry is silently dropped from the printed index. In both cases the mark, the entry key and the makeindex output are correct. D-003 already places output the index tool cannot consume with the extension and "a missing font" outside it by name, so the gap is IP2's wording, not the filter's behavior.
**Decision:** IP2's non-ASCII clause carries a condition — the document's PDF engine and main font must be able to draw the characters — and for terms outside Latin-1 that condition is the engine-and-font recipe README's `### Terms outside Latin-1` section names. The filter detects neither the engine nor the font and emits no warning when a term's script is uncovered; the remedy the extension offers is the documented recipe and the fixture that proves it, not detection. Detection would need an entry superseding D-003, not an amendment to this one.
**Consequences:** IP2 is amended in place and marked; KI6 narrows from "an engine and font decision this repo has not made" to the proven set and the unproven remainder, naming CJK and RTL. The DESIGN convention that calls non-ASCII terms appearing correctly an IP2 commitment picks up the same condition. An author indexing a non-ASCII term now has two document options to set and no warning if they do not — the cost this entry accepts. The recipe is proven by a typeset-print check for Greek, Cyrillic, and Latin beyond Latin-1 including terms written with combining marks; a script outside that set printing wrongly is a KI6 gap, not an IP2 defect, while a term in the proven set printing wrongly under the recipe remains the highest-severity class IP2 names. Reopening the detection question takes a superseding entry, whose evidence would be a path on which the filter can tell that a term's script is uncovered without reading the engine or the font.

### D-017 (2026-08-24): Quarto's default PDF engine is lualatex, and a half-set recipe fails silently (corrects D-016's context; its decision stands)

**Context:** D-016's context says that "under Quarto's default `pdflatex` a Greek index entry stops the render outright". M33's review found that false and this session re-probed it. Quarto 1.10.18 renders through LuaHBTeX; the pdflatex stop D-016 describes is reachable only by a document that names `pdf-engine: pdflatex` itself. Re-probed on M33's branch, `examples/unicode.qmd` with only its `pdf-engine:` line removed exits 0 and prints an index in which every term but the Vietnamese one is correct, and with both recipe lines removed it exits 0 and prints the Greek and Cyrillic terms as empty boxes. Evidence: `cairn/milestones/M33-non-latin1-terms.md`, and the `M33-AC4` no-engine control in `tests/run-tests.sh`.
**Decision:** D-016's decision stands unchanged — IP2's non-ASCII clause carries the engine-and-font condition, and the remedy stays the documented recipe rather than filter-side detection. What this entry corrects is the record of how that condition fails: setting neither line, or setting only the font, gives a build that succeeds while printing a term wrongly, not a build that stops. README's `### Terms outside Latin-1` section documents that third path, and the suite renders a control that pins it.
**Consequences:** the loud pdflatex stop is a signature an author reaches by opting into pdflatex, not the state a reader falls into by doing nothing, so the silent path is the one the section leads with for a reader who set one line and not the other. Nothing in DESIGN.md changes: IP2's amended wording and KI6 name the recipe and its proven set, neither of them a default engine. A future Quarto that changes its default engine again falsifies this entry's context and leaves D-016's decision standing.

### D-018 (2026-08-24): The non-Latin-1 recipe names STIX Two Text, and the covering font stays the author's install (trades GP3; annotates D-016)

**Context:** README's `### Terms outside Latin-1` section, which D-016 makes the source of IP2's engine-and-font condition, tells an author to run `tlmgr install stix`. `tlmgr info stix` reports that package obsolete since April 2018 in favour of `stix2-otf`. Both live in `collection-fontsextra`, outside a default TinyTeX, which GP3 ("LaTeX-side needs stay within packages bundled in mainstream TeX distributions") argues against. Probed at this plan gate: TeX Gyre Termes, which a default TinyTeX does ship, renders the fixture's Greek, Polish, Vietnamese and combining-mark terms correctly and drops Cyrillic entirely — eight `Missing character` lines and a blank where `Москва` should print.
**Decision:** the recipe names STIX Two Text, loaded by file from `stix2-otf`, and keeps the install step. A font covering Greek, Cyrillic and Latin beyond Latin-1 together is not in the core collections, so GP3 is traded here rather than satisfied: the extension documents the dependency and proves the recipe, and bundles nothing. The suite keeps refusing to run when the font is unfindable, rather than skipping the recipe renders — a skip line reads as a pass to anyone scanning the output, and this suite's evidence rests on nothing passing unrun.
**Consequences:** M34 carries the swap through README's block and prose, `examples/unicode.qmd`'s front matter, the claims rows, the font guard and the four controls, and re-proves the printed set under the new font; KI6's proven set is re-established there, not inherited. GP3 is unchanged as a principle — this is one stated trade under it, and the filter itself still needs nothing beyond Quarto. A contributor without `stix2-otf` cannot run the suite, which is the cost this entry accepts. Reopening takes a superseding entry, whose evidence would be a font inside a default TinyTeX that covers all three scripts, or a shipped Quarto default that covers them without one.

### D-019 (2026-08-24): a font-only recipe no longer fails silently, so the engine line is kept for a reason that is not today's output (corrects D-017's context and its decision's account of the failure; D-016's decision stands)

**Context:** D-017 records that setting the font and leaving `pdf-engine:` out gives "a build that succeeds while printing a term wrongly", probed under the `stix` font M33's recipe named. M34 swapped the recipe to STIX Two Text and re-probed the same control: it exits 0 and prints all eight of the fixture's terms as their own entry lines, `Việt` included. Re-verified at M34's review gate — the no-engine capture's producer is `LuaTeX-1.24.0`, so Quarto's default engine is still lualatex and what changed is the font's coverage, not the engine.
**Decision:** D-016's decision stands unchanged, and so does D-017's on which engine Quarto defaults to. What this entry corrects is D-017's account of how the condition fails: under the recipe as it now stands, omitting only the engine line is not a silent-failure path at all. README's `### Terms outside Latin-1` section says so, and tells the reader to set the engine anyway, because that line pins the behaviour to what the recipe states rather than to whichever engine their Quarto picks.
