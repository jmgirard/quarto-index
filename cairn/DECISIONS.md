### D-001 (2026-08-16): entry= values are structured format-neutral data, not raw LaTeX

**Context:** M01's plan made `entry="..."` a raw LaTeX pass-through (sub-entries written in imakeidx syntax). The design interview adopted IP1: mark values must be meaningful to every future back-end.
**Decision:** Entry values are structured data the extension parses and realizes per format (e.g., sub-entry separation interpreted by the extension itself, remainder escaped); raw back-end code is never accepted in mark values.
**Consequences:** M01's escaping-design scope needs a gated plan amendment before implementation. Future back-ends consume the same entry semantics. Admitting raw LaTeX later would require an explicit recorded reversal of IP1.

### D-002 (2026-08-18): An empty index level is not a level

**Context:** M11 found that a leading empty level in `entry=` (`entry="!Cats"`) made the LaTeX back-end emit a null field, which makeindex rejects — dropping the whole entry while exiting 0 with no warning. Three semantics had to be settled, and D-001 records this same class of choice about what `entry=` values mean.
**Decision:** An empty level prints nothing and is therefore not a level: it is dropped once, format-neutrally, before any back-end sees it. A value that is only empty levels falls back to the mark's visible text, or indexes nothing where there is none. A sort level is dropped together with the entry level it was written for, never re-aligned onto a level it was not written for; the loss is reported.
**Consequences:** `entry="!Cats"` and `entry="Cats!"` both index as `Cats`, in every back-end, and no entry can file under an empty string. Depth is counted after the drop, so a stray `!` cannot push an entry over the LaTeX three-level ceiling. The rule is format-neutral by its own justification — a level that prints nothing is not a level — and so lives in the shared parse layer, unlike the three-level ceiling, which stays in the back-end that imposes it. From the first tagged release this is IP3-bound syntax.

### D-003 (2026-08-19): Output the index tool cannot consume is the extension's, not the toolchain's

**Context:** M15 fixes a term marked both plainly and with a cross-reference, which makes the LaTeX back-end emit two rival encapsulations for one index key; makeindex rejects the pair and Quarto turns that into a failed render. GP2 says the contract ends at correct emitted output and that a toolchain's failure modes are documented, never detected or managed, which reads against fixing it at all.
**Decision:** A pair of commands the documented index tool provably cannot process is incorrect emitted output, not a toolchain failure, so repairing it sits inside GP2 rather than trading against it. The reading is deliberately narrow: it licenses changing what the extension emits when the extension's own output is unusable, never detecting or working around a failure the emission did not cause — a missing font, a distribution quirk, a user's own preamble.
**Consequences:** M15 proceeds without amending GP2. A later proposal to detect or manage a toolchain failure the extension did not cause is still governed by GP2 as written and needs its own justification. GP2's "known failure modes documented" continues to govern what the README says about failures this extension cannot prevent.


### D-004 (2026-08-20): Byte-level output-neutrality evidence is rejected as the refactor oracle

**Context:** `tests/byte-diff.sh` rendered every merge-base fixture twice and diffed the `.tex` byte for byte. Planning M17 (splitting the 2,729-line filter) asked whether to widen it to HTML and to the three book projects, which the 29-of-38 non-recursive fixture list, the non-hermetic base checkout, and the one-file clean-tree guard all left uncovered.
**Decision:** Widening was refused as the checker-regress shape, and the script is deleted rather than simplified: its own header disclaims it as a check, it duplicates coverage the ~100-check acceptance suite has, and a byte-diff fails on invisible whitespace changes — the shape tracking-rules names as a defect in the test ("a test that breaks under a behavior-preserving refactor"). The acceptance suite is the sole oracle for output neutrality.
**Consequences:** M17 verifies the split through the suite's pass/fail set plus an install-parity probe, with no merge-base output comparison; a rendered-output change no check probes would pass. That residual risk is recorded on the acceptance-suite hardening candidate row. Restoring byte-level evidence takes a superseding entry.

### D-005 (2026-08-20): Where a back-end folds levels, it judges cross-reference targets against what it prints

**Context:** M14 made the "target names nothing this document indexes" report format-neutral, resolving targets against the level paths the author wrote, on the grounds that whether a target names an indexed term is a fact about the document rather than about a back-end (IP1). M18 finds the LaTeX three-level fold breaks that in both directions: a target naming the folded path draws that report *and* the fold's own self-reference report, which contradict each other, and a target naming a written path the fold rewrites resolves silently while the printed index contains no such path. D-003 is the governing frame — a cross-reference the documented index tool prints and no reader can follow is incorrect emitted output, not a toolchain failure.
**Decision:** A back-end that folds levels folds cross-reference targets by the same rule and resolves them against the paths its entries print. The format-neutral report stands unchanged for every format that imposes no ceiling, and the format-neutral self-target comparison is untouched — M10's gate choice against moving that comparison into the back-ends still holds. Only the resolution set becomes back-end-relative, and only where a ceiling exists.
**Consequences:** In LaTeX the report no longer fires for the fold-induced shapes in `examples/self-xref.qmd`, superseding the last sentence of M14's AC4 for that back-end alone; HTML and back-end-less formats keep the counts M14 pinned, and the counts themselves live in M18's criteria. A future back-end with a ceiling inherits the rule; one without inherits nothing. D-002's placement rule is unchanged: the ceiling stays in the back-end that imposes it, and the empty-level drop stays shared. Restoring a single format-neutral resolution set takes a superseding entry.

### D-006 (2026-08-21): A reported level count names the levels it is over

**Context:** A value in `entry=`, `sort=` or a cross-reference target has three level counts — what the author wrote, what survives the empty-level drop (D-002), and what the LaTeX three-level fold prints. Three warnings name one of these and say which either not at all or misleadingly: the folded-target report names the post-drop count of a target the author wrote deeper (M18 review F9), and the extra-sort report attaches "before empty levels are dropped" to two counts no drop touches (M13 review F4). M13 shipped this subject once already and left both open.
**Decision:** A warning reporting a count of index levels names which levels the count is over, and gives the count the author wrote alongside it wherever the two differ. This governs what a number is called, never what it is: D-002's rule that depth is counted after the drop is unchanged, and so is every number these reports compute.
**Consequences:** The written count is carried to the two fold reports, which do not hold it today, so what `target_levels` and `drop_empty_levels` already compute travels to the LaTeX back-end. On a mark that both loses an empty level and crosses the ceiling, the empty-level report and the entry-fold report name the same pair of counts on consecutive lines; suppressing one would need the two reports to know about each other, and was refused. The rule binds the three reports M19 names and any later report that comes to name a level count. It was deliberately not mechanized as a sweep, because the message-distinctness scan cuts each message expression at `:format(` and so never reads its numbers — a gap recorded on the acceptance-suite hardening candidate row. A report whose count has no drop to distinguish is outside the rule.

### D-007 (2026-08-21): Per-locator styling leaves makeindex's encapsulation channel

**Context:** M20 gives one occurrence of a term an emphasized locator. Realized as a makeindex encapsulation, that breaks the render: makeindex's conflict predicate is same key, same page, any byte difference in the encapsulation string — bare-versus-encapsulated included — and a Pandoc filter cannot know page numbers. Distinguishing the principal mark through the key, the printed field or the sort field files it as a different entry instead, which corrupts the index rather than styling it. makeindex itself warns at exit 0 and writes a correct `.ind`; Quarto alone fails the render, on a regex over the `.ilg` transcript. RB01/RR01 (`cairn/reviews/archive/`) verified each leg.
**Decision:** Per-locator styling is not expressible through what `\index` commands say, and this back-end realizes it on a second, typeset-time channel instead: every locator mark of a key carrying a role emits one uniform per-key encapsulation, so a conflict is unreachable by construction rather than merely unexercised, and the role is registered from the mark's own position into the `.aux` and applied when the index is typeset. Warning-suppression and engine-swap recoveries are refused — each is blanket, masks the collision class D-003 covers, and is user metadata a filter cannot set anyway.
**Consequences:** M20 builds the subsystem; M21's page ranges inherit both the channel and its one known gap, a registered page folded inside a range printing unemphasized. The impossibility is permanent, so a later proposal to style a locator through the encapsulation channel is answered here rather than re-derived. Refusing the subsystem on cost leaves exactly one fallback — the LaTeX back-end reports the role as unrealized (IP1) — and taking it needs a superseding entry.

### D-008 (2026-08-22): An author-written range registers its own printed page string (annotates D-007)

**Context:** D-007 puts per-locator styling on a typeset-time channel: the principal mark writes its ordinal and `\thepage` to the `.aux`, and `\printindex` looks each printed page up in that registry. A page range prints as one string — `3--7` — which matches no per-page registration, so D-007 recorded a principal page inside a range printing unemphasized as the channel's one known gap and left it to M21.
**Decision:** That gap divides in two, and M21 closes only the half the filter can see. A range the AUTHOR wrote is known to the filter, so its opening and closing marks each register their own page, and the pair is composed into the printed range string and registered against the key's ordinal exactly as a single page is; the opening page is registered alone as well, since makeindex prints a same-page pair as one page rather than as a range. A range makeindex FOLDS out of consecutive pages is not known to the filter at all — no mark says a range exists there — and stays unemphasized.
**Consequences:** D-007's channel is extended, not superseded: the uniform per-key encapsulation, the ordinal and the registry are unchanged, and one further `.aux`-borne command joins the four. The prose recording the gap — README's principal-locator section and `core.lua`'s subsystem comment — narrows to the folded case, which is a correction of current knowledge rather than an addition. The ROADMAP candidate row asking whether a folded range is emphasized whole stands, now naming the only remaining half.

### D-009 (2026-08-22): A range pairs within one Pandoc process, never across a book's chapters

**Context:** M21's ranges pair two marks of one entry. In every format but an HTML book that pairing happens inside one Pandoc process — a single document is one process, and a PDF book is one merged document. An HTML book is not: each chapter renders in its own process, so the pairing has to be re-derived by whichever chapter reads the sidecar store. Three review rounds each found exactly one defect in that re-derivation, and each was the same mistake — a value resolved in one chapter's process read as raw in another's — in the record's `range` field, then the book's verdict, then the record's `role`. The store's per-mark record mixes what the author wrote with what that chapter concluded, and its current shape cannot express the boundary.
**Decision:** A range pairs within one Pandoc process and nowhere else. In an HTML book a `range=` mark indexes as though the attribute were absent, and the book says so once rather than pairing across chapters. This is not a judgement that cross-chapter ranges are undesirable; it is that pairing them needs a per-chapter record which separates the author's own values from a chapter's resolutions, and that design is not M21's to settle.
**Consequences:** D-008's Consequences say "one further `.aux`-borne command joins the four"; it is two — `quartoindexrangeat` and `quartoindexrangeto` are the names an `.aux` line carries, and the other two are emitted at the marks — and this entry supersedes that count, which matters because the stale-`.aux` exposure is counted in those names. M21 ships ranges for single documents in both back-ends and for PDF books, and the cross-chapter case leaves its scope. The candidate row promotes on that record shape rather than on the feature being wanted — the conflation is what produced one defect per review round, so a proposal that keeps the present record shape is answered here rather than re-derived, and takes a superseding entry. D-008's range registration is untouched: it is LaTeX-side and a PDF book is one document.

### D-010 (2026-08-22): A chapter's own range pairs in an HTML book (annotates D-009)

**Context:** D-009's Decision paragraph says "In an HTML book a `range=` mark indexes as though the attribute were absent." Written at the cross-chapter descope, the sentence overgeneralizes: a chapter is one Pandoc process, so a range whose two marks are in one chapter pairs there — shipped behavior M21's fixtures and README document.
**Decision:** That sentence narrows to a range whose marks are in different chapters. D-009's title — a range pairs within one Pandoc process, never across a book's chapters — already states the rule; everything else in D-009 stands.
**Consequences:** Reading only; no code or scope change.


### D-011 (2026-08-23): A source-shape scan is retired or narrowed, never widened

**Context:** The acceptance-suite-hardening candidate row carries five ways the `tests/scans/` checks miss what they read: four scans take the FIRST regex match over a source set that became multi-file at M17, so a stale duplicate definition masks the live one; the twelve-scan count pin counts files under `tests/scans/` rather than the source-reading sites it claims to hold, so a one-for-one swap passes it; `warn-distinct.py` cuts each message expression at `:format(` and so reads neither the numbers nor the text built there; the moved-definition probe writes every relocated definition into one `modules/moved.lua`, exercising one member of a nine-member family; and no check guards M17-AC1's one-definition-per-entry-point rule at all. Planning M25 asked whether to widen each of them.
**Decision:** Widening is refused, on D-004's precedent and for the same reason it gave. A scan that pins names and shapes in source certifies a property it never asserts — the M23 lesson, drawn from six such gaps found across two review rounds, every one of them by someone building the broken tree by hand while the scan exited 0. Each scan is therefore retired, or narrowed to what it reads with its header comment saying so. Where a property is positional, the evidence is a render: a render cannot pass a tree whose render fails.
**Consequences:** M25 removes the twelve-scan pin, disposes the four FIRST-match scans one at a time, narrows `warn-distinct`'s promise rather than teaching it to read `:format(` arguments, and leaves M17-AC1 unguarded by any scan. The coverage that leaves is coverage the scans only appeared to give; the residual risk — a source-shape regression no render probes — is recorded on the acceptance-suite-hardening candidate row beside D-004's own. This entry governs scans over the extension's SOURCE. It does not touch checks over rendered output, and M24's repair of where a check reads from is outside it entirely: that leaves every promise unchanged. Restoring a widened source scan takes a superseding entry.

### D-012 (2026-08-23): A same-tree state-pollution comparison is not the refactor oracle D-004 refused (annotates D-004)

**Context:** D-004 deleted `tests/byte-diff.sh` and closed with "Restoring byte-level evidence takes a superseding entry", leaving the acceptance suite as the sole oracle for output neutrality. M26 needs to prove that a document's index output does not depend on what ran before it in the same Lua state, and the only evidence that covers every one of the 17 accumulators — including `principal_emitted`, which reaches the preamble, and `principal_ordinals`, whose value reaches the `.aux` registry — is a byte comparison of two renders.
**Decision:** D-004's bar does not reach this comparison, and no superseding entry is needed. What D-004 refused was a MERGE-BASE oracle: two trees, differing by a refactor, compared byte for byte — the shape tracking-rules names as a defect in the test, because a behavior-preserving change breaks it on invisible whitespace. M26's comparison runs both sides off ONE tree, differing only in whether a test-only filter drove a synthetic document through the pass list first. A refactor moves both sides identically, so the failure mode D-004 named is unreachable here by construction, and the comparison's subject is the milestone's own deliverable rather than a proxy for it.
**Consequences:** M26's AC1 and AC2 rest on `cmp -s` over a captured `.tex` and a captured HTML page. D-004 is otherwise untouched: the acceptance suite remains the sole oracle for output neutrality across commits, `tests/byte-diff.sh` stays deleted, and its residual risk stays on the acceptance-suite-hardening candidate row. This entry licenses same-tree comparisons whose two sides differ only in a deliberately injected condition; a byte comparison across two commits still takes the superseding entry D-004 demands.

### D-013 (2026-08-23): A finding about current behavior is a known issue, not a candidate row

**Context:** Every review that found something appended it to the nearest `cairn/ROADMAP.md` candidate row or `cairn/LESSONS.md` line, because neither file's header said where a finding belongs and a candidate row was the only place accumulating them. Rows grew clauses that propose no work — how the extension behaves today, what a check does not cover — and both files reached their weight caps; M27's file records the sizes and the per-row figures.
**Decision:** Three records divide the material. `cairn/DESIGN.md`'s `## Known issues` holds a statement about how the extension or its acceptance suite behaves today, a gap in what a check covers included; each entry carries a stable `KI<n>` label, its own text, and the review it came from. `cairn/ROADMAP.md`'s `## Candidates` holds work this repo might do — one row stating the work and its promotion condition, pointing at the `KI<n>` labels that motivate it and restating none of them. `cairn/LESSONS.md` holds transferable craft, a mistake a future milestone could repeat, and never a fact about this repo's present state; a lesson that has become one takes the ownership exit to `## Known issues`.
**Consequences:** A row that proposes nothing is not a candidate — its content is a known issue and the row does not exist. A review recording a finding writes a `## Known issues` entry, and a candidate row only where it wants work done. `KI<n>` labels are assigned in order and never reused, so a pointer survives an entry being reworded; the milestone that closes an issue strikes its entry and rewrites any row pointing at it in the same commit. The `## Candidates` comment in `cairn/ROADMAP.md` and the header comment in `cairn/LESSONS.md` name this entry. This governs where a record goes, not what is kept: M27 moved every clause and dropped none.

### D-014 (2026-08-23): A reported block or chapter position names the sequence it counts (annotates D-006)

**Context:** D-006 made a warning reporting a count of index LEVELS say which levels the count is over, and left outside its rule any report whose number has no empty-level drop to distinguish. Three reports sit in that gap: the emptied-place and duplicate-marker reports in `marker.lua` name a top-level-block position, and the chapter-count report in `book.lua` names a number of chapters. Nothing said what any of those numbers is counted over, and the `resolve_markers` comment and the `marker-shapes.qmd` manifest comment both called the block position the author's own. It is not: Quarto expands includes and executable cells before any filter runs, and `examples/marker-position.qmd` holds a marker written as its third top-level block and reported at its fifth.
**Decision:** A warning reporting a position or a count over a sequence names that sequence. A block position says it is counted over the document as this filter received it, after Quarto expanded any includes and executable cells, so it can differ from the position in the author's source file; a chapter count says it is over the files the book renders, in the order the book's render list gives them. Where a report names two numbers, each is named where it is printed. The author's own source position is not offered alongside the reported one: the expansion has already happened by the time the filter runs and nothing records where a block came from, so the report qualifies its number rather than printing a second one it cannot compute.
**Consequences:** The block-position clause is one shared string in `marker.lua`, so the two reports there cannot drift apart. The evidence is emitted text in captured render logs and never a scan of the filter's source, which is D-011's rule and the reason no check here reads a `warn` literal. KI21 narrows to the injection kinds no fixture exercises; KI25 closes. Naming the chapter FILE in a book report is M29's subject, not this entry's. A later report that comes to name a position or a count over a sequence inherits the rule; a report whose number indexes into no sequence is outside it, as it is outside D-006.

### D-015 (2026-08-24): `[` and `]` stay out of the LaTeX escape table

**Context:** Pandoc's LaTeX writer escapes `[` and `]` in body text, and the filter's `LATEX_LITERAL` table does not carry them. KI1 recorded that gap from M01 and called it harmless in practice without saying what had been tried, and a ROADMAP candidate row asked for the two characters to be added. The concern behind the row is real in shape: `theindex` builds its entries with `\item`, and a `\item` that takes an optional argument would swallow a leading `[`.
**Decision:** The two characters stay out of the table. Probed at this plan gate under the engine the extension ships against, with `imakeidx` loaded: index entries leading with a bracket, holding one medially, and trailing a closing bracket each compiled through both LaTeX passes, were accepted by makeindex without rejection, and typeset in the index exactly as written. `theindex` redefines `\item` without an optional argument, which is why the leading case survives. Escaping them anyway would change what an entry sorts under and ripple through the probe set and several manifests, for no behavior a reader can see.
**Consequences:** KI1 is struck and its candidate row removed. `PROBE_CHARS` and `LATEX_LITERAL` keep the 16 characters they name, and `tests/scans/latex-escape-table.py` keeps holding the two to each other. This settles the two brackets, not the table: a character shown to print wrongly is an IP2 defect and joins the table on that evidence. The gap the row actually sat on — that the suite proves all 94 printable ASCII characters compile and are accepted, and proves only 16 of them print — is M30's subject, not this entry's. Reopening takes a superseding entry, whose evidence would be a shipping document class or package whose `theindex` `\item` takes an optional argument.

### D-016 (2026-08-24): IP2's non-ASCII promise is conditional on the document's PDF engine and main font (narrows IP2; annotates D-003)

**Context:** IP2 promised that any characters in a visible term appear correctly in the index, non-ASCII included, with no condition attached. Probes at M33's plan and implement gates show that promise is false as written, and not because of anything the filter does: under Quarto's default `pdflatex` a Greek index entry stops the render outright with `not set up for use with LaTeX`, and under `xelatex` with the default main font the render succeeds at exit 0 while every glyph the font does not carry is silently dropped from the printed index. In both cases the mark, the entry key and the makeindex output are correct. D-003 already places output the index tool cannot consume with the extension and "a missing font" outside it by name, so the gap is IP2's wording, not the filter's behavior.
**Decision:** IP2's non-ASCII clause carries a condition — the document's PDF engine and main font must be able to draw the characters — and for terms outside Latin-1 that condition is the engine-and-font recipe README's `### Terms outside Latin-1` section names. The filter detects neither the engine nor the font and emits no warning when a term's script is uncovered; the remedy the extension offers is the documented recipe and the fixture that proves it, not detection. Detection would need an entry superseding D-003, not an amendment to this one.
**Consequences:** IP2 is amended in place and marked; KI6 narrows from "an engine and font decision this repo has not made" to the proven set and the unproven remainder, naming CJK and RTL. The DESIGN convention that calls non-ASCII terms appearing correctly an IP2 commitment picks up the same condition. An author indexing a non-ASCII term now has two document options to set and no warning if they do not — the cost this entry accepts. The recipe is proven by a typeset-print check for Greek, Cyrillic, and Latin beyond Latin-1 including terms written with combining marks; a script outside that set printing wrongly is a KI6 gap, not an IP2 defect, while a term in the proven set printing wrongly under the recipe remains the highest-severity class IP2 names. Reopening the detection question takes a superseding entry, whose evidence would be a path on which the filter can tell that a term's script is uncovered without reading the engine or the font.

### D-017 (2026-08-24): Quarto's default PDF engine is lualatex, and a half-set recipe fails silently (corrects D-016's context; its decision stands)

**Context:** D-016's context says that "under Quarto's default `pdflatex` a Greek index entry stops the render outright". M33's review found that false and this session re-probed it. Quarto 1.10.18 renders through LuaHBTeX; the pdflatex stop D-016 describes is reachable only by a document that names `pdf-engine: pdflatex` itself. Re-probed on M33's branch, `examples/unicode.qmd` with only its `pdf-engine:` line removed exits 0 and prints an index in which every term but the Vietnamese one is correct, and with both recipe lines removed it exits 0 and prints the Greek and Cyrillic terms as empty boxes. Evidence: `cairn/milestones/M33-non-latin1-terms.md`, and the `M33-AC4` no-engine control in `tests/run-tests.sh`.
**Decision:** D-016's decision stands unchanged — IP2's non-ASCII clause carries the engine-and-font condition, and the remedy stays the documented recipe rather than filter-side detection. What this entry corrects is the record of how that condition fails: setting neither line, or setting only the font, gives a build that succeeds while printing a term wrongly, not a build that stops. README's `### Terms outside Latin-1` section documents that third path, and the suite renders a control that pins it.
**Consequences:** the loud pdflatex stop is a signature an author reaches by opting into pdflatex, not the state a reader falls into by doing nothing, so the silent path is the one the section leads with for a reader who set one line and not the other. Nothing in DESIGN.md changes: IP2's amended wording and KI6 name the recipe and its proven set, neither of them a default engine. A future Quarto that changes its default engine again falsifies this entry's context and leaves D-016's decision standing.

### D-018 (2026-08-24): The non-Latin-1 recipe names STIX Two Text, and the covering font stays the author's install (trades GP3; annotates D-016)

**Context:** README's `### Terms outside Latin-1` section, which D-016 makes the source of IP2's engine-and-font condition, tells an author to run `tlmgr install stix`. `tlmgr info stix` reports that package obsolete since April 2018 in favour of `stix2-otf`. Probed at this plan gate: TeX Gyre Termes, which a default TinyTeX does ship, renders the fixture's Greek, Polish, Vietnamese and combining-mark terms correctly and drops Cyrillic entirely — eight `Missing character` lines and a blank where `Москва` should print.
**Decision:** the recipe names STIX Two Text, loaded by file from `stix2-otf`, and keeps the install step. A font covering Greek, Cyrillic and Latin beyond Latin-1 together is not in the core collections, so GP3 is traded here rather than satisfied: the extension documents the dependency and proves the recipe, and bundles nothing. The suite keeps refusing to run when the font is unfindable, rather than skipping the recipe renders — a skip line reads as a pass to anyone scanning the output, and this suite's evidence rests on nothing passing unrun.
**Consequences:** M34 carries the swap through README's block and prose, `examples/unicode.qmd`'s front matter, the claims rows, the font guard and the four controls, and re-proves the printed set under the new font; KI6's proven set is re-established there, not inherited. GP3 is unchanged as a principle — this is one stated trade under it, and the filter itself still needs nothing beyond Quarto. A contributor without `stix2-otf` cannot run the suite, which is the cost this entry accepts. Reopening takes a superseding entry, whose evidence would be a font inside a default TinyTeX that covers all three scripts, or a shipped Quarto default that covers them without one.

### D-019 (2026-08-24): a font-only recipe no longer fails silently, so the engine line is kept for a reason that is not today's output (corrects D-017's context and its decision's account of the failure; D-016's decision stands)

**Context:** D-017 records that setting the font and leaving `pdf-engine:` out gives "a build that succeeds while printing a term wrongly", probed under the `stix` font M33's recipe named. M34 swapped the recipe to STIX Two Text and re-probed the same control: it exits 0 and prints all eight of the fixture's terms as their own entry lines, `Việt` included. Re-verified at M34's review gate — the no-engine capture's producer is `LuaTeX-1.24.0`, so Quarto's default engine is still lualatex and what changed is the font's coverage, not the engine.
**Decision:** D-016's decision stands unchanged, and so does D-017's on which engine Quarto defaults to. What this entry corrects is D-017's account of how the condition fails: under the recipe as it now stands, omitting only the engine line is not a silent-failure path at all. README's `### Terms outside Latin-1` section says so, and tells the reader to set the engine anyway, because that line pins the behaviour to what the recipe states rather than to whichever engine their Quarto picks.

**Decision:** the override is a nested `labels:` map holding `symbols`, `see` and `see-also`, accepted at the document's top level and inside one `indexes:` entry, with the nearer setting winning key by key rather than map by map. The map's name states what kind of value its keys hold, so the keys keep matching the mark attribute names without inheriting their meaning. Two levels with nearest-wins is one mechanism scoped the way `lang:` itself already is, not a parallel syntax. The flat top level of an index declaration is left for per-index settings that are not reader-facing words. The plan gate's per-index-only answer is superseded by this entry at a second gate where the review's case was put to the user verbatim.

**Consequences:** a fourth reader-facing string — the locator punctuation an Arabic index would set, which is a ROADMAP candidate and not this work — joins `labels:` without claiming a top-level name. A document-level `labels:` applies to every index, so a document wanting two indexes worded differently writes the difference per index and the shared part once. The map is validated the way an index declaration already is: an unusable shape is reported and falls back, never half-installed. Falsified by an author needing a per-index setting these keys cannot express, or by the two levels proving indistinguishable in practice, which would make the document level the only one worth keeping.

### D-037 (2026-08-28): an index heading with no declared title localizes too, and IP3 governs syntax forms rather than printed defaults (narrows IP3)

**Context:** an index with no `title:` is headed `Index` in HTML and EPUB and by babel's `\indexname` in LaTeX, since `index.lua:424` emits `\makeindex[intoc]` with no `title=`. So the heading already follows the document's language in one back-end. Localizing the labels and not the heading would reproduce in miniature the asymmetry this work removes. Against that, 0.1.0 released 2026-08-26 and IP3 makes documented syntax forms changeable only through a deprecation cycle, which raised whether a changed printed default is such a form.

**Decision:** the untitled heading resolves through the same table as the labels, in the same release, with `title:` remaining the author's absolute override. IP3 governs the syntax an author writes, not the words the extension prints: no syntax form changes here, and a document renders identically unless it declares a non-English `lang:`, in which case its PDF already localizes. The change is recorded in the changelog as a change to default output. The conservative reading — holding the heading one release behind the labels — was put to the user and declined, on the review's ground that shipping localized labels under an English heading is the worst of the three states.

**Consequences:** IP3's boundary is now stated where a later milestone can read it, and a future change to a printed default is an ordinary changelog matter rather than a deprecation cycle. The visible change is confined to languages whose word differs from `Index`, so `fr` and `de` documents see nothing. An author who pinned the English heading by relying on the default rather than writing `title:` sees it change; writing `title: Index` restores it, which the changelog entry says. Falsified by an author reporting a broken cross-reference or link that depended on the English heading text, which would show the printed default carrying more contract than this entry grants it.

### D-038 (2026-08-28): only the heading an undeclared document falls back to localizes; a declared index without a title keeps its own name (narrows D-037)

**Context:** D-037 wrote its decision as "an index with no `title:` localizes", from a context paragraph describing only the undeclared document. The two are not the same set. A declared index that writes no `title:` does not fall back to the English `DEFAULT_TITLE` at all: `read_declaration` sets that index's title to its own `name`, an author-written string. That name also reaches the LaTeX back-end, through `\makeindex[title={...}]` at `index.lua:419-430`, which is gated on `is_declared()` and so is never reached by an undeclared document. M057's criteria audit found the plan freezing the narrower set while D-037's sentence promised the wider one.

**Decision:** the localization replaces the `DEFAULT_TITLE` an undeclared document falls back to, and nothing else. A declared index that writes no `title:` keeps falling back to its own `name`, untranslated: that name is text the author wrote, not a default this extension chose, and a table has no business overriding it. This is why no table row can reach the LaTeX back-end — the only heading the table supplies is the one `is_declared()` excludes from `\makeindex[title={...}]`.

**Consequences:** an author who declares an index, writes no `title:`, and wants a localized heading writes the heading — which is the same instruction they already have for wanting any particular heading. D-037's decision stands as to the undeclared document, which is the case its context argued; this entry narrows its sentence to that case rather than superseding it. Falsified by an author reporting that a declared index's `name`-derived heading reads as an untranslated default rather than as their own text, which would show the two sets should have been treated alike.

### D-039 (2026-08-28): the override map is `index-labels:`, because `labels:` at a document's top level is Quarto's own (amends D-036)

**Context:** D-036 named the override map `labels:`, accepted at a document's top level and inside one `indexes:` entry. M056's first render showed the name is taken: Quarto injects a `labels:` map into every document's metadata carrying nine title-block strings of its own — `abstract`, `affiliations`, `authors`, `description`, `doi`, `keywords`, `modified`, `published`, `related_formats` — and a filter reading the top-level key sees them whether or not the author wrote anything. The unknown-key report D-036's validation calls for fired nine times on a document that declared nothing at all. A probe confirmed `index-labels:` and `index:` both reach the filter unclaimed.

**Decision:** the map is `index-labels:`, at both levels. Everything else D-036 settled stands unchanged: a nested map rather than flat fields, the three keys `symbols`, `see` and `see-also`, two declaration levels, the nearer setting winning key by key, an unusable shape reported and fallen back from rather than half-installed. A top-level `labels:` is Quarto's map and this extension does not read it. Two alternatives were declined at the gate: nesting `labels:` inside a new top-level `index:` map, which would put a settings map one letter from the existing `indexes:` list of declarations; and staying inside Quarto's map, which would cost the document-level unknown-key report and leave a future Quarto label spelled `see`, `see-also` or `symbols` silently setting an index word.

**Consequences:** the name an author writes is one word longer than D-036's, and is the same word at both levels. The name is IP3-bound syntax from the release that ships it, so this amendment is free only because it lands before that release. An author who guesses `labels:` gets Quarto's map and no index word, which is why the documentation states the collision by name (M056-AC7). Falsified by Quarto claiming `index-labels:` for itself, or by an author reporting that the two keys read as one surface.

### D-040 (2026-08-30): an index no marker names goes to the book's last chapter, not the last chapter that places one (supersedes M55's placement choice)

**Context:** M55 chose to hand an index no placement marker names to the last chapter of the book that places an index, so that every index section of a book would sit in a chapter its author had asked for one in. Which chapter that is has to be worked out from the sidecar store, and each chapter of an HTML book renders in its own process: the chapters before a given one have written this render's records, the chapters after it still hold the previous render's. Two chapters of a single render can therefore reach two different answers, which is KI199 — a chapter that gains a marker between two renders is printed a section by the chapter ahead of it as well as by itself. M60 held the adoption back until a chapter had read a usable record for every chapter after it, which turned the doubling into a section printed in no chapter at all on a first render, and M061 added two reports to say which case had happened. A chapter whose record can never be written left the section unprinted for ever.

**Decision:** the fallback chapter is the last chapter of the book — `ctx.chapters[#ctx.chapters]`, the end of the render list Quarto hands every chapter — provided some chapter of the book places an index. It is the same value in every chapter's process on every render, so no two chapters can disagree and no render can print such a section twice or not at all. The two reports M60 and M061 built for the disagreement are retired with the record fields they read; `STORE_VERSION` does not move, so a record carrying those fields keeps its chapter's terms. Declined at the gate: reading later chapters' `.qmd` source for a marker, which recognizes a marker by text and is blind to one arriving through an include or an executable cell; and a per-render store snapshot, which adds a store artifact and a one-render lag.

**Consequences:** an index no marker names can now print in a chapter its author asked nothing for — the book's last chapter, whatever is in it. That is the price of an answer no two chapters can disagree about, and the remedy is a marker for that index wherever the author does want it. IP3 is not amended: D-037 narrows it to syntax forms rather than printed defaults, and this moves a printed default. A book with no placement marker anywhere still grows no section. Falsified by an author reporting that their book's last chapter is a place an index section must not appear, and that writing a marker elsewhere is not an acceptable answer.

### D-041 (2026-08-30): a chapter's own source is read where its record cannot be used (supersedes D-040's declined clause)

**Context:** D-040 declined reading a chapter's `.qmd` source on two grounds — that it recognizes a marker by text, and that it is blind to one arriving through an include or an executable cell. Both were stated where source-reading would have decided WHERE a fallback section goes, a judgement a missed marker moves silently. KI205 and KI214 record what the store-only route costs instead: a section printed short the terms of any chapter whose record cannot be read, and no section at all where the last chapter can read a usable record for no chapter that places one.

**Decision:** a chapter whose record the building chapter opened and could not use has its source read and parsed, and the marks and placement markers that parse yields join the book's index. D-040's first ground does not hold here: the parse is an AST walk with the extension's own mark reader, not text recognition. Its second stands and is this rule's boundary — a mark or marker reaching a chapter through an include shortcode, an executed cell, or content the HTML render drops is not recovered, and the documentation says so. Recovery never fires on an absent record, so a first render is unchanged; only the author's own values are recovered and never a chapter's conclusions (D-009, D-021); and a recovered mark's locator carries the chapter's page with no fragment.

**Consequences:** supersedes D-040's declined clause and nothing else in it — the fallback chapter is still the book's last, and some chapter placing an index is still the proviso, now settled from the book's chapters rather than only from the records that could be read. The store stays the primary route and the only one carrying anchors. A read-only tree that has never been rendered leaves every record absent, so KI205 narrows rather than closes. Falsified by a recovered term reaching an index where the rendered page does not carry it.

### D-042 (2026-08-30): recovery skips Quarto's conditional content whole (narrows D-041)

**Context:** D-041 gave as its boundary that a mark reaching a chapter through an include shortcode, an executed cell, or content the HTML render drops is not recovered, and named a recovered term reaching an index whose page does not carry it as its own falsifier. M064's review reproduced exactly that: a mark inside a `::: {.content-visible when-format="pdf"}` div was recovered and printed in the book's index, linking to a page that does not carry it. The reader walks the file on disk, and the file on disk records nothing about how Quarto settled that block's visibility.

**Decision:** every block and span carrying Quarto's `.content-visible` or `.content-hidden` class is taken out of the parse whole, before any mark or marker is read, whatever its `when-` or `unless-` attributes say. A mark inside one is not recovered even where the render in hand would have printed it. Losing a term an author wrote is accepted over putting a term in the index whose page does not carry it.

**Consequences:** narrows D-041's boundary clause from content the HTML render drops — a class nothing here enumerates — to the two conditional-content classes, which the reader does enumerate; the documentation states the narrower thing. Every other route by which a render drops content is outside what this rule promises. Falsified, as D-041 was, by a recovered term reaching an index where the rendered page does not carry it.

### D-043 (2026-08-31): a store directory that is there and unusable is not an absent record (extends D-041)

**Context:** D-041 fires source recovery where a chapter's record was opened and could not be used, and never where it is absent — the boundary that leaves a first render unchanged. `store_read` decided which by whether opening the record path returned a handle, and that test cannot tell a record that was never written from one sitting in a store directory replaced by a file or whose permissions were cleared: both return nothing. A book in that state lost every chapter's marks from every other chapter's index, silently and on every render — the cost KI205 records for one chapter, paid by all of them, with no report saying so.

**Decision:** before a record is treated as absent, the store directory itself is probed: it is unusable when it cannot be listed and its own name appears in a listing of its parent. Where it is unusable, every record this render cannot open is treated as opened-and-unusable, so each chapter is recovered from its source and reported by the existing unreadable-record report. Where the directory is not there at all — a first render, a tree never rendered — the name is not in the parent listing and the absent branch is taken exactly as before. The probe reads no error message, and runs once per rendering chapter rather than once per record. Declined: a report of its own for the store directory, which is a fourth wording to place, count and translate for a state one line of the existing report already names per chapter.

**Consequences:** extends D-041's trigger to cover the store directory as well as the record file, and leaves its never-fires-on-absent clause standing, since a directory that does not exist is not unusable. In that state every chapter parses every other chapter's source on every render, which grows with the square of the book's chapters; it is a state the author ends by removing the offending path, and the alternative is an index silently short most of its terms. Falsified by a first render, or a tree with no store directory, drawing a recovery report.

### D-044 (2026-09-01): a record whose name the store directory lists and which cannot be opened is not an absent record (extends D-043)

**Context:** D-043 asked the store DIRECTORY whether a record this render could not open was written or never written, and answered from whether the directory could be listed. Listing a directory needs its read bit and opening a file inside it needs its search bit, so a directory that lists perfectly well can hold records nothing can open — a store whose search bit is gone, or one record whose own permissions were cleared. KI221 records that state: the record reads as absent and its chapter's marks go missing from every other chapter's index, silently and on every render, which is the cost D-043 set out to end paid one chapter at a time instead of all at once.

**Decision:** the evidence a record was written is its own filename appearing in a listing of the directory it belongs in. A record `io.open` cannot open whose name is among those entries is treated as opened-and-unusable, so its chapter is recovered from its own source and reported by the existing unreadable-record report; a record whose name is not there is absent exactly as before, so a first render and a tree with no store are untouched. D-043's directory-level test is kept whole inside the same probe — a directory that cannot be listed while its own name is in its parent's listing puts every record under it out of reach — and its cost rule is kept as stated: the listing is remembered per directory, so a render lists the store once however many records it meets there. The listing consulted is the record's OWN directory rather than the store's top level, because a chapter in a subdirectory has its record in a matching subdirectory of the store and two chapters of one filename share a record basename. Declined at the plan gate: reading the error `io.open` returns, which is a message string this extension would be parsing.

**Consequences:** extends D-043's trigger from the store directory to the record file. A file merely NAMED like a record and unopenable — a broken symlink an author left at that path by hand — now counts as written and has its chapter recovered; nothing Pandoc's Lua interface exposes separates it from the real thing, and no render this extension makes produces a file of that name it cannot open, so the state arises only where something else made it and its cost is a chapter recovered rather than dropped (KI224). Falsified by a first render, or a tree with no store directory, drawing a recovery report — D-043's falsifier, unchanged and now also covering a store directory that lists and holds no record for the chapter in hand.

### D-045 (2026-09-02): a record no render has written is recovered in the chapters that can print an index section (supersedes D-041's never-fires-on-an-absent-record clause)

**Context:** D-041 fires source recovery where a chapter's record was opened and could not be used, and never where it is absent — the clause that leaves a first render unchanged, kept whole by D-043 and D-044 as they widened what counts as "there". KI205 records what absence still costs: a book rendered into a tree whose records never survive, and a book rendered a chapter at a time, print an index short the terms of every chapter no record has been written for, silently and on every render. A chapter's marks reach the index by no other route, so nothing else can end it.

**Decision:** a record whose name no listing of the directory it belongs in carries is recovered from its chapter's source in the reading chapter when that chapter carries a placement marker of its own, or is the book's last chapter; in every other chapter it is read as absent exactly as before. Between them those two are every chapter that can PRINT an index section, which is the only place a missing chapter's terms are lost rather than merely unread. Both halves are known before the store is opened — the marker set from `resolve_markers`, the position from `ctx.position` against `ctx.chapters` — so no two chapters of one render can disagree about either, and the gate asks the store nothing. A chapter recovered this way draws a fourth wording naming the record as one no render has written; a never-written record whose source parses and reaches no mark is silent, because a chapter that marks nothing is indistinguishable from it and reporting it would fire for most of a correct book on every render; a never-written record whose source cannot be read draws the existing wording for that outcome. Declined: recovering an absent record in every chapter, which makes a chapter that prints nothing parse the whole book to no end.

**Consequences:** supersedes D-041's never-fires-on-an-absent-record clause and nothing else in it; the falsifier D-043 and D-044 both carry is restated against the gate rather than against absence — falsified by a first render, or a tree with no store directory, drawing a recovery report in a chapter that carries no placement marker and is not the book's last. A whole-book render is untouched, since each chapter reads the store after the chapters before it have written, so an ordinary first render of a book whose marker sits in its last chapter recovers nothing and reports nothing; a book whose markers sit earlier does recover, and says so. The accepted cost is that a chapter which prints no section still sees a store one chapter short, which nothing renders and nothing reports (KI205, narrowed to it). Where the store has never been written, one chapter parses every other chapter's source, the cost D-043 already accepts for an unusable store directory, unmeasured at book sizes.

### D-046 (2026-09-02): recovery reads a chapter source named `.qmd`, `.md`, `.markdown` or `.Rmd` and refuses every other kind (narrows D-041)

**Context:** D-041 has a chapter's own source read where its record cannot be used, without saying which files that covers, and `recover_record` handed whatever it found to Pandoc's markdown reader. A Quarto book may take a notebook chapter, whose file on disk is JSON. KI219 recorded what that cost: a one-cell `.ipynb` chapter's raw JSON parsed as markdown yields a span whose `index` attribute carries the JSON's own quoting, which matches no index the book declares, and the term is filed into the book's first index with nothing said — recovery resolves the name before `fold_undeclared` would draw the refiling report.

**Decision:** before anything is opened, the chapter path's own extension is lower-cased and looked up in an enumerated set — `.qmd`, `.md`, `.markdown`, `.Rmd` — and a chapter outside it is not parsed at all; a chapter whose name carries no extension is refused with the rest, there being nothing to test it against. Such a chapter is refused rather than recovered, and reported by a wording of its own naming the file and the accepted set, drawn once per reading chapter ahead of every other store wording, so a refused chapter says one thing rather than two and is never handed on as a stale record. Declined at the plan gate: sniffing the file's content, which would be a second reader guessing at a format Quarto already names.

**Consequences:** narrows D-041's "a chapter's own source" to a set the code enumerates, so recovery no longer files a term under a name nothing in the book answers to. The refusal parts company with D-045's silence rule: a refused source was never read, so nothing knows whether it marks a term, and staying silent would cost its author every term of that chapter with no way to find out — a book carrying a notebook chapter therefore hears about it on every render whose store is missing that chapter's record. The refusal is reached only where D-041, D-043, D-044 or D-045 already sends a chapter to its source, so a notebook chapter whose record is present and usable is read from that record like any other, which is what a whole-book render leaves behind. It stands ahead of the version-skew branch, so a refused chapter can never draw the different-version wording (KI234). Falsified by a Quarto release taking a book chapter whose extension is outside the set and whose source Pandoc's markdown reader reads correctly.

### D-047 (2026-09-02): what a recovered chapter's parse yields includes the marks in its front matter (narrows D-041; extends D-042)

**Context:** D-041 has the marks that parse yields join the book's index, and `recovered_marks` walked `parsed.blocks` alone. Probed 2026-09-02 under pandoc 3.11: a filter table carrying a `Span` function visits a span in `abstract:` exactly as it visits one in the body, and visits it before the body. So a mark an author writes in a chapter's front matter is indexed by that chapter's own render, and was silently missing from every index of the book whenever the chapter was recovered instead — the recovery route departing from the render, which is what D-041 exists to avoid.

**Decision:** `recovered_marks` walks the chapter's metadata and then its blocks, in that order, so a sort key declared in front matter beats one declared in the body exactly where it beats it in the ordinary render; the order is stated by two walks rather than read off Pandoc's traversal. D-042's conditional-content removal reaches the metadata too, through the same named filter, so a front-matter mark carrying or inside `.content-visible` or `.content-hidden` is not recovered although that chapter's own render does index one. `recovered_markers` is NOT widened with it: `resolve_markers` reads `doc.blocks` alone, so a marker in front matter places nothing in the ordinary render either, and reading one here would be the departure this rule is closing. Declined at the plan gate: narrowing the ordinary render so that neither route indexes a front-matter mark, because the render's behavior is what a single-document author already gets and changing it would drop terms from documents that are not books at all.

**Consequences:** narrows D-041 by saying what "that parse yields" covers, and extends D-042's drop from the blocks to the metadata — so the conditional class is one the recovery route now diverges on in front matter as it already diverges on it in the body, deliberately, preferring a lost term over one whose page does not carry it. The two routes still differ in how many locators they file: Quarto reflects a chapter's `abstract:` into its body before this extension runs, so the record route files such a mark more than once and the source route once (KI232, KI233). Falsified by an author reporting a term written in their front matter reaching the index as a defect rather than as what they asked for.

### D-048 (2026-09-02): a front-matter mark in an HTML book chapter files one locator, the chapter's page (narrows D-047's consequences; annotates D-041)

**Context:** D-047 has the ordinary render and the recovery route both index a mark written in a chapter's YAML front matter, and records as a consequence that the two differ in how many locators they file. KI232 and KI233 record what the render's count costs: probed 2026-09-02 under quarto 1.10.18, Pandoc hands the `Span` passes a front-matter mark before any body span, and Quarto also copies some fields (`abstract:` among them) into a hidden top-level div `#quarto-meta-markdown` that nothing survives in, so one `abstract:` mark files three locators of which two link to ids the page does not carry, and a `description:` mark files one dead locator because the book's title block does not print that field. The filter cannot tell, at the time it runs, which fields the page will print. In a single document there is no reflected div and every probed field prints its anchor.

**Decision:** in an HTML render of a book chapter, a mark the metadata walk reaches is filed once, with a locator that is the chapter's page and no fragment, and mints no anchor — the way the recovery route already files it (D-041); the copies Quarto reflects into `#quarto-meta-markdown` are not marks, their index class removed before any pass reads them. A single document is untouched: its front-matter marks keep their anchors and fragments. Declined at the plan gate: keeping the metadata copy's fragment and dropping only the reflected copies, which leaves the link dead for `description:` and any field the title block does not print, a set the filter cannot see; and a fragment for an enumerated list of printed fields, which is Quarto's title-block template and drifts by release and theme.

**Consequences:** a chapter read from its record and one recovered from its source now print the same rows for a front-matter mark, and D-047's locator-count consequence no longer holds. A link from the index to a mark in an abstract lands at the top of the chapter's page, where the title block is, rather than at the abstract's own anchor, which survived. The removal of the reflected copies' class is made in HTML renders only; what the other back-ends do with those copies is unmeasured. Falsified by an author reporting that a front-matter link landing at the top of its chapter's page is a defect, or by a Quarto release that stops removing the div, which would leave the copies on the page unindexed.

### D-049 (2026-09-02): a refused chapter whose record another version wrote is reported once per index section (supersedes D-046's count clause; its precedence clause stands)

**Context:** D-046 has a chapter whose source kind the recovery route will not read reported by a wording of its own, drawn once per reading chapter ahead of every other store wording, whatever state its record was in. KI234 records the cost: the three different-version wordings are drawn once per chapter that builds an index section, and once by a chapter whose records show no chapter placing any index (M062), so a book with many chapters and one notebook chapter whose record an older version wrote says the refusal once per chapter where it says any other stale record once per section.

**Decision:** on the version-skewed branch the refused chapter is handed back to the report site with the stale records and drawn there, under the same gate, ahead of the three different-version wordings and with the refusal's own wording. The never-written and the unopenable and undecodable states keep the inline draw and the counts they have, which are the counts their sibling wordings follow. D-046's precedence clause stands whole: a refused chapter says one thing, and it is never the different-version wording. Declined at the plan gate: a seventh wording naming both the refusal and the version, since the record's state decides nothing an author acts on differently; and leaving the count as it is.

**Consequences:** supersedes only D-046's "drawn once per reading chapter" clause. A render of a chapter that builds no section over a store whose only fault is a notebook chapter's old record says nothing, exactly as it says nothing about any other stale record. Falsified by an author reporting they needed to know that a refused chapter's record was stale rather than merely unusable.

### D-050 (2026-09-03): a store report names the record state the render can evidence, and only a numeric version evidences a version (supersedes D-045's never-written-and-unreadable-source clause)

**Context:** D-045 gave a never-written record its own wording where its chapter's source came back, and sent the case where that source cannot be read to "the existing wording for that outcome" — the sentence saying the recorded marks could not be read, which asserts a record file that no render ever wrote. KI230 recorded the cost: an author whose store has never been written and one of whose chapters is unreadable is sent looking for a corrupt record that is not there, which is the same falsehood the never-written wording was added to avoid one branch earlier. KI236 recorded its sibling on the other axis: `store_read` classified a record as written by another version on `data.version ~= STORE_VERSION`, and a record file decoding to a table with no `version` field satisfies that test, so a truncated or hand-emptied record was reported as carrying a version it does not carry.

**Decision:** each store report names the state the render can evidence about the record it met, and no more. A record no render has written whose chapter's source cannot be read draws a sixth wording of its own, saying that no render has written the record and that the chapter's source could not be read either; the wording for a record that WAS written and could not be read is left to the case where a file really was there. And a record reads as written by another version only where its `version` field holds a number this render does not itself write: a field that is absent, a string or a boolean evidences no version at all, and such a record joins the wordings for one that could not be read. `valid_record` is deliberately not narrowed with it — usability asks whether this render can read the record, and every one of these was already refused and read back from its chapter's source — so the narrowed test decides which report is drawn and nothing else. Declined at the plan gate: reusing the could-not-be-read wording for the never-written case, which asserts a record existed; and a seventh wording for a record whose bytes are a table with no version, since the distinction buys nothing an author acts on differently.

**Consequences:** supersedes D-045's clause that a never-written record whose source cannot be read draws the existing wording for that outcome, and nothing else in D-045 — where and how often the never-written reports are drawn is untouched. The six wordings the never-written and could-not-be-read families now hold are mutually distinct and none is a prefix of another, which `tests/scans/warn-distinct.py` holds at its pinned count. No record's usability changes and no index gains or loses a term: both changes move which sentence an author reads. Falsified by an author reporting that the two never-written reports read as unrelated to them, or that they needed to know a versionless record held a record's bytes rather than a damaged record.
